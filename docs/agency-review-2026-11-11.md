# 汇通云：涉税服务机构业务、匹配与归档评审

评审日期：2026-11-11。对象为本次工作目录的实际代码，GitHub 基线 `c6e33d2`、版本 3.2.6，以及本地整改。此前其他目录的服务器归档重构没有合并到此代码，不能作为本系统已经具备的能力。

## 管理结论

系统已有较实用的凭证采集、原件阅读、规则匹配、分录分摊、人工复核和 PDF 阅读册功能。但当前业务记录和原件仍以浏览器为主要保管位置，服务器主要保存账号。它适合继续做本地业务验证；作为多客户涉税服务机构的统一生产档案平台，还缺客户账套隔离、服务器原件库、独立复核、完整移交与恢复能力。

本轮优先修复会造成错配、重复占用或档案失真的确定性问题，同时换用用户确认的松绿与米白主题。自动匹配应满足对象、金额、方向、账号、日期和唯一性约束；不能确定的关系必须说明原因并转人工。

## 一、匹配功能：先保证关系正确

### 1. 真实复现的高风险问题

| 编号 | 修复前的具体反例 | 整改要求 |
|---|---|---|
| M01 | 一份 150 元回单，R09 先分摊 100 元给凭证甲，R06 又按 150 元整单给凭证乙，合计占用 250 元 | 统一按真实关系计算余额；整凭证规则只能使用完全未占用的金融单据；同轮、历史及跨期占用均参与校验 |
| M02 | 甲客商凭证 100 元，乙客商回单 150 元，只因本企业银行账号和日期相符，便自动截取 100 元 | 收款核回单付款人，付款核回单收款人；分录客商优先，辅助核算和凭证总客商不能冲突；缺失和代收代付转人工 |
| M03 | 100 元整额回单与 40＋60 元组合同时存在，系统只选整额并称“唯一” | 整额与组合一起寻找完整解；发现第二解即转人工，不按导入顺序抢单 |
| M04 | 单独一张 150 元回单被 100 元分录自动截取，缺少实际业务分摊依据 | 保留人工部分分摊及后续余额使用；自动分配必须形成有充分对象依据的完整唯一解 |
| M05 | 纯引擎输入未标识红字的负金额仍可能进入分摊 | 引擎自身校验金额符号、红字标识、作废状态，不能只依赖导入页保护 |

本轮对应变更位于 `entryAttachments.ts`、`matchingEngine.ts`、`matchPlanCore.ts` 及专项回归测试。完整通过结果以本次验收说明为准。

### 2. 必须区分的关系

- **入账依据**：发票等原始凭证支持一笔或多笔会计分录，累计入账金额受约束，不能重复报销入账。
- **结算依据**：银行收付款与债权债务清偿相关，允许分次、合并、部分结算，需要维护可用余额。
- **共享资料**：合同、审批等可被多张凭证引用，不参与金额凑算。
- **企业名称归集**：只方便按单位查找资料，不表示金额、分录附件或真实性已核对完成。
- **正式归档成员**：经过准入核验后固定原件、关系、元数据和成员，之后不能随当前列表变化。

当前数据模型已区分结算分摊与共享引用，但发票“入账占用”和“付款参考”的用途还没有完整独立建模。应继续补充稳定的分录 ID、关系用途、原交易 ID、撤销原因和版本，避免把同一发票在付款凭证中的参考引用误当重复入账，或反向漏掉真正重复入账。

### 3. 自动匹配的业务顺序

1. 限定机构、客户、账套、币种及业务方向，排除已锁定、作废和无效来源。
2. 优先继承源 ERP 的稳定关联与交易标识，再核对票据唯一标识；名称文本只能作为辅助。
3. 用整数分校验金额、已占用和剩余额度；不同用途分别核算，不混加发票、回单和共享合同。
4. 核对外部往来对象、本企业银行账号和收付方向；禁止将“本企业账号命中”当作“外部客商命中”。
5. 在明确窗口内检查业务日期与期间。跨期有合理场景，必须保留原业务日期和归属，不能改日期来凑匹配。
6. 统一检索一对一与组合解，并检查其他凭证的竞争。多解、超限和信息不足转人工。
7. 记录命中条件、排除原因、规则版本、关系金额和人工依据；规则评分不能当作实测准确率。

当前代码缺少客户/账套及币种等基础范围字段，因此第 1 步仍有结构性待办。现有唯一性判断只在当前输入数据和受支持搜索上限内成立，不能推断“全球唯一”或“没有遗漏原件”。

### 4. 需要专项模型的复杂业务

| 场景 | 正确处理路径 | 当前应采用的边界 |
|---|---|---|
| 第三方代收代付、集团资金池 | 保存委托或协议、实际付款方、受益方和被清偿债务 | 转人工；不能因同账号、同金额或近似名称自动确认 |
| 银行手续费、净额到账 | 分清交易毛额、净额、手续费及对应会计分录 | 人工逐分录核对；不得放大金额容差掩盖差额 |
| 外币收付和汇兑损益 | 原币、本位币、汇率来源和时点分别记录 | 待专门币种模型，不跨币种自动凑算 |
| 红字发票、退款、撤销、重新开具 | 保存原交易与冲销链；区分红字入账和实际资金退款 | 负金额本身不能证明退款关系，需人工核对原交易 |
| 一票多期入账、预付款和尾款 | 发票入账占用与结算占用分账维护 | 可人工使用分摊基础能力，专门的用途与跨期链继续建设 |
| 工资、个税、社保等批量业务 | 批次清单、员工明细与汇总分录相互勾稽 | 批量合计相等不能替代明细核对，专项模板待建设 |
| 本企业多银行账户互转 | 同一业务的收付款两端、在途资金与费用分别核对 | 不按普通外部客商规则自动猜测 |
| 应计、折旧、结转、暂估 | 内部计算表、审批依据和无需外部附件的原因 | 允许有依据的人工豁免外部附件；记账凭证自身原件仍须保留 |
| 税款缴纳、缴款书、财政票据、差旅票据 | 扩充票种字段和业务唯一标识，保留结构化电子原件 | 当前只有发票/回单/合同/审批四类，不应强制伪装成普通发票 |

上述边界也是场景覆盖的一部分。支持人工处理时，应能留下明细金额和依据；尚无对应字段的专项业务必须明确列为待建设，不能声称已完整自动覆盖。

## 二、归档与票据专业性

### 1. 发票载体与核验

纸质扫描件、电子发票、数电发票和无法确认的票据必须分别表达。缺少可见发票章不能一律否定电子发票；未知类型也不能直接免章放行。本轮增加载体、核验结果、核验依据及经办信息，并把入口调整为“核验发票”。

人工登记“已核验”只是经办人员声明，不能显示为系统已经接通税务查验或自动完成数字签名验证。后续应保存官方查验结果或验签证据及其来源、时间、结果版本；票据作废、红冲和状态变更需要重新触发检查。

这一设计依据包括[国家税务总局关于电子专票采用电子签名代替发票专用章的答复](https://www.chinatax.gov.cn/chinatax/n810356/n3255681/c5160347/content.html)、[数电发票推广公告](https://fgk.chinatax.gov.cn/zcfgk/c100012/c5236067/content.html)。核验仍须结合具体票种和原件内容，不能只看文件扩展名或票面是否出现“电子”二字。

### 2. 正式档案不能只有整理页

此前没有上传影像的结构化记录也能生成信息页并写入锁定状态。信息页可以帮助阅读，但不能代替缺失的原始凭证。本轮增加正式生成前的实际原件检查，缺件时不创建成功档案或保留成功锁定；新档案固定成员与阅读记录快照。

另一个已复现问题是范围补号：归档“记-1”至“记-3”后再导入“记-2”，新凭证可能被范围锁定，却不在原 PDF 中。本轮阻止向已锁定范围补导凭证。历史档案未曾记录成员快照的，应做迁移核验，不能悄悄改写历史。

### 3. 原件、派生件和完整档案包

原件应保留原始字节、文件大小、入库摘要、来源、上传人和时间。拆页、压缩、OCR、阅读 PDF 都是派生版本，要记录父原件与处理步骤。导出 PDF 的 SHA-256 只能检查该 PDF 的一致性，不能独立证明发票真实、原件从未变更或形成了法定时间戳。

正式交付包至少包括原件、派生阅读册、目录清单、结构化元数据、分录及金额关系、核验/复核记录、版本、审计记录和文件校验清单。应提供包校验和恢复演练，不能把 CSV 或阅读 PDF 当作全量备份。

按照[财会〔2020〕6号](https://www.mof.gov.cn/zcsjtsgb/gfxwj/202003/t20200323_3583778.htm)，仅电子形式处理有合法真实、安全防篡改、完整接收元数据、必要审签和防重复入账等条件；打印使用电子凭证时也需保留相应电子凭证。[《会计档案管理办法》](https://www.mof.gov.cn/gp/xxgkml/tfs/201512/t20151214_2510365.htm)还涉及长期保管、备份、纸电关联与利用管理。据此，本报告建议将原件库、备份恢复及档案生命周期列为平台建设要求。

### 4. OFD/XML 与电子凭证标准

目前文件验证主要支持 PDF、PNG、JPG；OFD、XML 及嵌入结构化数据的处理仍需建设。应先做到安全接收和原样保存，再逐步增加解析、验签、可视化和元数据导出，不能只保留转成的截图。

[财会〔2025〕9号](https://www.mof.gov.cn/jrttts/202505/t20250521_3964264.htm)及[推广应用版电子凭证会计数据标准](https://kjs.mof.gov.cn/zt/kuaijixinxihuajianshe/dzpzkjsjbzshsd/sjbz/202505/t20250519_3964020.htm)提供了结构化电子凭证的适配方向。财政部还发布了[电子凭证会计数据标准应用验证系统](https://kjs.mof.gov.cn/zt/kuaijixinxihuajianshe/dzpzkjsjbzshsd/gjb/202602/t20260204_3983327.htm)，后续可据此制定对接和验证清单；本轮代码没有宣称通过该验证。

## 三、机构业务与团队操作

### 必须具备的管理链

客户建档与授权 → 委托期间和服务范围 → 资料接收及交接清单 → 缺件催收 → 账证整理 → 匹配与异常处理 → 经办自检 → 独立复核 → 客户确认 → 归档与交付 → 借阅和移交 → 到期鉴定及依法销毁。

代理记账客户会计档案与机构自身的涉税执业档案需要分别管理：专项服务还应保存委托约定、取数口径、专业判断、工作底稿、三级或适当级别复核、报告版本、沟通与交付记录，不能仅以“已匹配凭证”替代。

[《涉税专业服务管理办法（试行）》第十六条](https://fgk.chinatax.gov.cn/zcfgk/c100011/c5239044/content.html)涉及内部控制、质量管理与风险控制。上述流程和岗位划分是据此并结合机构业务提出的系统设计建议，并非认为添加几个状态按钮即可满足全部执业要求。

### 岗位与权限

应以客户/账套授权为基础，区分经办、复核、归档、借阅、移交和管理员。归档前记录复核人、时间、范围、版本和结论，重要业务防止经办自行最终复核。管理员账号不应天然获得随意覆盖原件、删除历史审计和跳过所有财务校验的能力。

当前管理员/普通用户两类账号尚不足以表达这些职责；同浏览器财务仓库也没有按用户、客户和账套隔离。这是 P0 结构性待办，本轮局部修补和换色没有解决它。

### 操作体验

- 待办按客户、期间、经办人、缺件原因、超期天数组织；优先给出可执行下一步。
- 匹配界面应同时可看凭证、分录、候选原件、外部收付款人、账号、金额与剩余额度。本轮补充候选的客商约束说明。
- 批量操作先显示影响范围、成功与失败清单，并保留失败重试，不用一个总计掩盖部分失败。
- 将“已关联资料”与“已生成档案册”分开显示。名称归组仅表明归属；规则评分仅用于规则判断和排序。
- 附件份数、扫描张数和 PDF 页数分别记录；一份三页合同不能随意当作三份金融单据。
- 保留已挂载草稿、窗口缩放、键盘焦点、窄屏列表与减少动态支持；长列表避免用低对比的小字堆叠。

## 五、实施与验收顺序

### 第一阶段：本轮本地整改

修复已复现错配与占用问题；补完整解歧义、红字边界、原件准入、发票分类、档案范围保护和 CSV 安全测试。采用松绿与米白主题，改善图标、短反馈、状态表达及窄屏。

### 第二阶段：机构生产基础

完成服务器权威业务库和原件库、客户/账套及岗位授权、版本冲突与幂等、审计、备份恢复；制定旧浏览器数据的迁移映射、校验清单和回滚方案。新旧数据必须逐项核对，不能直接把另一分支的实现整体覆盖进来。

### 第三阶段：专项业务与规模化

补充入账/结算/参考用途、第三方收付、手续费、外币、红冲原交易链、工资税费批次、电子凭证结构化标准及机构执业档案。以真实脱敏业务样本建立标注集，分别测自动命中、误配和人工兜底结果。

### 验收必须看到的证据

- 每类场景有输入、期望关系、金额占用、处理方式、失败原因和测试出处，详见配套场景矩阵。
- 无错误主体关系、无超额占用、无同单重复入账；第二解明确转人工。
- 修改、撤销、刷新与再次执行不会丢失人工确认或偷偷重挂旧关系。
